# The Legend of Zelda: Ocarina of Time (`0400486024DEC000`)

A Switch 2 game: update v131072, SDK 22.2.8 (`Ounce`). Nintendo EPD's engine (sead, agl, gsys, Havok, CRIWARE; project `Owl`, with Tears of the Kingdom's file layout) on NVN2. Modules `main`, `subsdk0` (NintendoSDK_movie) and `sdk`, no rewriter patches. Status: plays on the Mac through the title, the opening, a new file's first scene, Link's house and Kokiri Forest, with saves, at about 59 fps with the picture close to console video. Mac only so far.

## Frame rate

The game's frame loop steps a constant per frame, so it played in slow motion below 60 fps. A stub now takes the measured frame time when that is longer ([A fixed step per frame runs slowly below the target](../../../docs/reference/frame-rate.md#a-fixed-step-per-frame-runs-slowly-below-the-target)); `DM_FRAME_DELTA=0` turns it off. Found by gunvalk in [Lichii PR #216](https://github.com/zortos293/Lichii/pull/216).

- **Render scale:** `DM_RENDER_SCALE=0.5`–`1.0` fixes the 3D views at that fraction of the game's size (1536x864 at 1.0, so 0.75 is 1152x648) and turns its dynamic resolution off; 1.0 or unset keeps the game's own. Two stubs (`patches.py`) in the graphics module's frame update (`main+0x31d3200`): at `main+0x31d3f38`, where the dynamic-resolution controller's ratio (`main+0x805aa0`, which reads its levels, counters and `LoadThreshold` from `game__gfx__DynamicResolutionParam`) and the game's forced 0.75 and 0.5 modes join to become the views' scale, the ratio is replaced with the host's; at the controller's status (`main+0x31d3ee4`) a host scale not yet applied makes the first frame recompute the sizes (at a steady frame rate the controller never asks). [seedds/nxnative#1903](https://github.com/seedds/nxnative/pull/1903) found the same function and store independently and multiplies at the store instead. Every reader of the scale (the view sizes, the other readers of module `+0xe5c`) sees the one value, so the render targets stop changing size, which ends the 1580 → 1579 → 1578 churn below. Not yet measured on a run: the stub is checked by executing it (`test_oot_real_speed.py`) and against the real `main`'s bytes.
- **Static shadow map size:** `DM_SHADOW_MAP_SIZE=4096`-`12288` (multiples of 1024; unset, 0 or 12288 keep the game's) makes the game's fine static depth shadow texture, a 12288x12288 Depth16 render target (296 MB of graphics memory, which tvOS counts against the app), that size: 6144 takes it to 74 MB, 4096 to 32 MB (saving 222 and 264 MB). The game has two such textures (the samplers `cSamplerFineStaticDepthShadow` and `cSamplerCoarseStaticDepthShadow`); the fine one's 12288 is a literal in its code, not the `StaticSdwWidth` parameter (4096), at `main+0xc30c24` / `main+0xc30c2c` (width and height in the texture info of the function at `main+0xc30870`) and `main+0x344d78` (the render target call `main+0xc2f3f0`). Three `mov wN,#0x3000` stubs (`patches.py`, state `+0xa0`) put the host's size in their place, so the game allocates the smaller texture and sizes its viewports from it; the coarse 4096x4096 one and the other depth targets are left alone. The game's static shadows get blurrier. Not yet seen on a TV: the shaders' and the update code's use of the map was read for literals (none found), not run.

### GPU time and passes in Kokiri Forest (2026-11-09)

Measured on a Mac mini M2 Pro (the Apple TV 4K's GPU generation) with the TV-like settings (handheld mode, `DM_RENDER_SCALE=0.5`, `DM_SHADOW_MAP_SIZE=6144`, the encode thread, the TV's texture and heap caps), the `balcony-still` route (Link's balcony, Kokiri Forest below, standing still), `scripts/bench.py`, two runs a side, the GPU held by one run at a time. The frame holds 2 vsyncs (33.3 ms) on the Mini, so the changes show in GPU time, not frame rate.

- Where the GPU waits: the encoder stamps of `DM_NVN_GPUPROF` showed 6.8 ms idle in a 24.3 ms span; Metal System Trace puts it at about 2.8 ms of a 25 ms frame, the rest being vertex work before passes stamped after their vertex stage ([GPU profiles time the frame's command buffers](../../../docs/reference/rendering.md#gpu-profiles-time-the-frames-command-buffers)). Of the real idle, about 1-1.3 ms is between command buffers: the frame's first big command buffer and the main scene submission were committed after the GPU had run out (the host still recording them), and a few were committed in time but started 0.3-0.5 ms late. The rest is inside command buffers, mostly between a compute encoder and the next pass. The resource-alias flush that every encoder barrier carried for the 2.4 GB pool held in chunks cost about 0.8 ms of GPU a frame (`DM_NVN_VIS_ALIAS=0`, diagnostic: GPU p50 23.41 → 22.64 ms).
- The game submits each frame on four queues; queue 1's job is split into about 22 submissions by its event waits and signals with queue 5's compute, and each is a Metal command buffer (37 a frame).
- The 960x540 RG11B10F scene target (with its Depth32F) was opened 19 times in a dumped frame (`DM_NVN_PASSDUMP=4200` with `DM_NVN_PASSDUMP_ALL`, which now names the caller that ended each pass). What came between two of its passes:
  - other targets drawn in between (light masks, shadow cascades, bloom, the ground mist): 6;
  - a queue boundary (an event wait or a fence sync, the async compute of queue 5 between, such as the ambient cache's image writes and the exposure): 4. A Metal command buffer ends there, so the pass must. Merging across them would need the waits resolved at encode and the other queue's dispatches moved ahead;
  - a draw that samples an attachment of its own pass (same-pass feedback, a snapshot or a split): 4;
  - a dispatch that samples the depth the pass just drew (`70f8568719810874`, occlusion culling): 1, it must stay;
  - the depth attachment changing (the main depth and a second 960x540 depth): 1;
  - the masked indirect multi-draw's compute (`mdx_run`) in the middle of the main lit pass: 1, it could run before the pass (open);
  - a culling dispatch (`93b8cf2a4840b5f2`) that samples a depth the pass does not attach: 1, movable in principle, but the draws before it read textures by handle, so the hoist cannot prove it ([the wider scan](../../../docs/reference/rendering.md#compute-dispatches-between-the-draws-of-a-pass-run-ahead-of-it) moves nothing here);
  - a clear-only pass landed by a dispatch that writes only a storage buffer (`a361c4347e39b1c3`): 1, gone with `DM_NVN_LAZY_CLEAR_WIDE=1` ([lazy clears](../../../docs/reference/rendering.md#lazy-clears-folded-into-the-next-pass), which also keeps the clears a texture bind landed: 121 → 119 passes, 4.1 MB less loaded and stored a frame).
- Measured changes (base GPU p50 23.4-23.5 ms, span 26.5-26.8 ms, 121 passes, 160.5 MB loaded and 167.4 MB stored a frame; the pictures alike, the scene being animated; two A/B sessions):
  - `DM_NVN_ALIAS_DIRTY=1` ([the alias flush only after writes](../../../docs/reference/rendering.md#the-resource-alias-flush-only-after-gpu-memory-writes)): GPU p50 23.53 → 23.16 ms, span 26.8 → 26.2 ms;
  - `DM_NVN_EMPTY_SUB=1` ([submissions with no GPU work](../../../docs/reference/frame-rate.md#submissions-with-no-gpu-work)): span 26.8 → 25.3 ms, GPU p50 23.53 → 23.18 ms, with one unexplained run of slow frames;
  - `DM_NVN_CUT_FIRST=16 DM_NVN_CUT_DISPATCH=1`: span 26.5 → 25.9 ms in the first session, 26.8 → 26.4 ms in the second (noisy);
  - `DM_NVN_LAZY_CLEAR_WIDE=1`: 2 passes and 8.2 MB a frame fewer, GPU time within noise;
  - all four together: span 26.8 → 25.2 ms (6%), GPU p50 23.53 → 23.20 ms, 119 passes;
  - `DM_NVN_CS_HOIST_WIDE=1`: nothing moved; `DM_NVN_POOL_UNWIRE=0`: no gain.

  The frame stays at 2 vsyncs on the Mini, so none changes its frame rate there; on the Apple TV, GPU-bound at 57-85 ms, each ms of span counts, and the pass traffic weighs more on its memory bandwidth. All stay off by default until run on the TV.


## Quality options for slower GPUs

Two switches that trade a little picture for GPU time, both off (full quality) by default on every platform. They are stubs of the frame step rule in [`patches.py`](patches.py), placed by their functions' fingerprints (`others` of the rule), and the rewriter declares the `GROUND_MIST` and `REFLECTION_INTERVAL` capabilities when it places them. Measured on a Mac mini M2 Pro with the TV-like settings (`balcony` save, the 657 frame shaders as tv-all builds them, 2026-11-09), each option switched on and off every 300 frames inside one run (two separate full-quality runs differed by 1.4 ms, more than the smaller savings). GPU is the frame's command buffers added up (`@gpu_ms`), span the first start to the last end; means over about 1,700 frames a side. The Apple TV 4K's GPU is about 3-4 times slower, so expect about that many times the saving there (not measured on the TV).

- **Ground mist (`DM_GROUND_MIST=off`):** the haze over Kokiri Forest's floor is a fluid volume. agl's `eularian_fluid_simulation` computes it (about 80 dispatches, 0.24 ms) and its drawer (`main+0x26b110` on v131072, called by the scene's draw with `[scene+0xb80]`) first draws its own half-size depth (three passes) and then ray-marches the volume in one task / mesh draw (fragment `5ad65c0eefd09c7f`: 43 memory lookups a pixel, 1.8 ms at 480x270) into the half-size translucent effects targets. The drawer returns at once unless its byte `+0x18` is 1; the stub makes it read 0 (state `+0xa4`). The simulation still runs: Foliage, Model and FoliageShader shaders sample its velocity (`cFluidSimulationVelocity`), so grass keeps moving with it.
  - Off: GPU 19.45 → 17.25 ms (-2.2), span 22.50 → 21.00 ms (-1.5); 121 → 117 passes. From the balcony the soft white haze over the distant floor is gone, and the floor reads a little clearer and darker. Down on the forest floor (walking down the ladder, where Saria stops Link) the haze is thick over the path and the left of the view, and without it the floor is clearly darker and more saturated: there the mist is part of the look. Nothing else changes.
  - Half rate and a lower resolution are not possible: the mist is added into the effects targets, which are cleared and shared with the other effects every frame, so there is no picture of the mist alone to keep for the next frame or to draw smaller. The game's own `ExecuteGraphicsFluidSimulationReduce` event command was found but not followed; `VolumeFogResScaleHandheld` / `Console` belong to the volume fog (`volume_fog`, compute `9e6b00b0`, 0.3 ms), not to this mist.
- **Reflection probes (`DM_REFLECTION_INTERVAL=2`-`8`):** the scene's reflection probes are cube maps of the surroundings (128x128 a face, `CubeMapMaxTexWidth`; two sample points, `_probe0` / `_probe1` in `CubeMapMgrParam/Common`). The scheduler (`main+0x33d6a0`) keeps per probe slot the faces done and the faces to have done after the frame, and hands out a budget of faces each frame (one per slot; seven at once for a few frames after a scene change). The draw (`main+0x268d10`) renders each face as a scene pass of about 220 draws (2.8 ms on the Mini, its pixel shaders make 72 memory lookups a pixel), then the filter chain (seven mips), and the slot is released two frames later. On the balcony: a face on each of 6 frames, the filter on the 7th, one idle frame. The stub replaces the budget load: on frames whose number (the host's present count, state `+0xac`) is not a multiple of the interval the budget is 0, so no probe moves on; the cycle stretches to about 7 x the interval frames. A smaller probe does not make a face cheaper: 64x64 faces (`CubeMapMaxTexWidth` 64 in `/gsys/ModelSceneConfigParam/Main.gsys__ModelSceneConfigParam.bgyml`, served through `DM_ROMFS_OVERLAY`; the game sizes the cubes, faces and filter chain from it) cost 2.17 ms against 2.03 at 128x128 on the Mini, Link's house (the pass is paid per draw, not per pixel). What halves a face is testing depth before its pixel shaders run (`dmsh_build.py` `ps_host_early`: 2.03 → 0.96 ms).

  | Interval | GPU (ms) | Span (ms) | A probe catches up in |
  |---|---|---|---|
  | 1 (the game's) | - | - | 8 frames |
  | 2 | 19.42 → 18.68 (-0.74) | 22.81 → 21.94 (-0.88) | about 15 frames |
  | 4 | 19.84 → 18.80 (-1.04) | 22.96 → 21.45 (-1.51) | about 29 frames |
  | 8 | 19.50 → 18.33 (-1.16) | 22.90 → 20.84 (-2.06) | about 57 frames |

  Standing still the probes converge to the same picture, so the shots match (their difference is the scene's own animation: mean 2.6-2.8 against 2.6-4.2 between two full-quality runs). What changes is how soon reflections follow a change of light or place. The frames that still render a face keep its whole cost; the option lowers how often they come.
- Recommended for the Apple TV 4K: the mist off (the largest saving, at a small visual cost) and an interval of 4 (most of the probe saving; an interval of 8 adds little).
- Not wired into the launcher yet: a launcher setting would be a row each in [`dm/games/settings.tsv`](../settings.tsv), shown on `fixups:GROUND_MIST` / `fixups:REFLECTION_INTERVAL` (a toggle with `on`/`off`, a choice `1,2,4,8`), and the player's page `docs/settings.md`.

## Dynamic resolution

- The controller (v131072; found by fingerprint, so the addresses are only for reading): the parameters are `game__gfx__DynamicResolutionParam` (`LoadThreshold`, `ReduceCounterMax`, `IncreaseCounterMax`, and a list of levels, each a `ResolutionReduceScale` and a `Priority`). Once a frame the update (`main+0x805aa0`) reads the frame's GPU time, subtracts what its cost model predicts at the current size and keeps the trend of that residual. The level function (`main+0x8065e0`) adds the residual to the model's cost at each level and returns the best level under the threshold: 0, the full 1536x864, when the current size fits. The update moves down after `ReduceCounterMax` frames that ask for it and back up after `IncreaseCounterMax`. Scripted `GPULoad` hints from event data (`main+0x31c3de0`) and `OneshotSetDynamicResolutionLoadThreshold` adjust it in cutscenes.
- Resolved on the host: after a loading screen it sat at its floor, 683x384, for minutes while the frame held 60 fps with GPU time to spare. A stale frame-start timestamp and event waits that idled the GPU made its timer read more than the frame took: [Dynamic resolution at its floor while the GPU has time to spare](../../../docs/reference/frame-rate.md#dynamic-resolution-at-its-floor-while-the-gpu-has-time-to-spare).
- Resolved in the game's model: with the host's timer right it still sat at 683x384 for good. The update takes the frame's load (about 0.2 ms a unit) less its small fixed-cost model, divides the rest by the square of the current scale, and the level function multiplies that back by each level's scale squared. The whole remaining cost is taken to grow with the pixel count, as on the Switch 2 its constants were tuned for. Here it hardly does: 683x384 cost 14.3 ms and 1536x864 14.7 ms on an M4 Pro (mesh, compute and the upscaler's fixed 2048x1152 dominate). A probe of the controller in play (levels 0..9 at 0.75..0.333 of 2048x1152, threshold 83, about 16.4 ms) read a load of 70-80 at 683x384, under the threshold. The extrapolation still put full size at 300-400, so it never stepped up.
- Current: the launcher's **Dynamic resolution** (`DM_DYNAMIC_RESOLUTION`, off by default). Off holds full resolution. On climbs one level at a time on the load measured at each level, with no model of how the cost grows, within the game's own level list, threshold and counters:
  - down when the load has been over the threshold for 8 frames in a row, and that level is marked as not fitting;
  - up when the load fits and the level above was never measured, fitted when last measured, or was measured more than about 10 s ago.

  Nothing is decided until a level has held 8 frames, since the load is read a few frames late. The 8 frames in a row keep a single slow frame, or the first frames at a new size, from rejecting a level that fits. An earlier version stepped down on 2 frames over and stopped at level 2 after one burst to 90 at level 1. A version that stepped up only when the load, scaled by the next level's pixel ratio, stayed under the threshold sat at the floor too: 70 × 1.3 is over 83. Result (M4 Pro, 2026-11-09, `kokiri-still`, the full library on chain a02f1e0dfdde): from the floor to full size, then mostly at 1536x864. The load there is about 83, the game's own threshold, so a sustained frame over moves it to level 1 (0.70) for about 10 s. 59.9 fps, all 1,800 frames held at one vsync, frame p99 16.89 ms, GPU p50 14.5 ms. Loads by level: 72 at the floor, 75 at level 6, 80 at level 2, 82 at level 1, 83 at full size.
- Open: in heavier scenes it goes down to the floor for nothing. In the player's session (M4 Pro, 2026-11-09, Metal HUD) it held full size at loads of 80-84 until a scene took it to 94-102. It then stepped down to 683x384, where the load was still 83-86, about the same as at full size. It stayed near the floor at about 80 until a lighter scene (55 at the floor) let it climb again. The frame rate held about 60 throughout. The cost that decides the load here does not follow the resolution. The fix is to step down only to a level measured cheaper than the current one and otherwise climb back. Until then off, full size, is the better default on this Mac. Slower Macs, where resolution may matter, are not measured.

  It is a stub of the frame step rule in [`patches.py`](patches.py) that replaces the level function. It is placed by that function's fingerprint and the update's (it reads the update's fields `+0x8` and `+0x174`). The rewriter declares the `DYNAMIC_RESOLUTION` capability when it places the stub.
- Where the full-resolution GPU frame goes (M4 Pro, Metal System Trace, 2026-11-08): vertex/mesh 4.9, fragment 5.2, compute 4.3 ms per 1/60 s, and they do not overlap (their union is 14.4 ms, their sum 14.4). The heaviest passes: the main mesh pass (task `a5288d0a6c4971fd`, mesh `3439aaa071d868ae`, fragment `a1a56cf6d62ae798`), two foliage passes (task `47f9b38490dcf9a2`), and the upscaler's compute (`fa3033d05c0a41d6`, 177 HMMA calls, already on `simdgroup` matrices). Ruled out: the stage serialization is mostly the game's own barriers (about 70 a frame, 39 of them `ORDER_PRIMITIVES | INVALIDATE_TEXTURE`). The relaxed draw-pass barriers of `draw_barriers game` are off whenever an image family heap exists (this game's dynamic-resolution depth buffer makes one). Keeping them on with the alias flush moved to a start barrier skipped 22% of the full barriers, but the real GPU span did not change (14.7 ms p50 either way, two runs each), so that change was not kept. Also ruled out: mesh shaders writing only the vertices their primitives use (the highest index + 1, instead of all `max_v`), as an overlay of the 31 play mesh shaders against the same shaders recompiled: span 14.7 / 15.5 ms against 16.0 / 15.6, so the game's meshlets are full. A shader timeline needs the trace attached before the pipelines are made, and a recording from 3 s to the play window (9 GB, or 45 s with the shader profiler) never finished saving.
- Measured on the M4 Pro (20-core GPU, 2026-11-08, `kokiri-deck`, one run each): at full resolution (the main passes 1536x864 in pass dumps at 75, 100 and 125 s) 48.1 fps, frame p50 16.74 / p95 33.41 ms, GPU p50 15.0 / p95 16.9 ms: the GPU needs about one vsync a frame, so the frame step holds 2 vsyncs much of the time. ## Open

- Root cause confirmed on M4 Pro (2026-11-08): [ignored event waits](../../../docs/reference/nvn-objects.md#gpu-event-waits-order-work-across-queues) let lighting consumers run before their producers. The game issues about 25 waits and 19 signals per frame. All 297 complete traced frames submit queue 5's ambient-cache consumer `9e6b00b050e30801` before queue 1's SH producer `21d9f83e6027c565`, despite the explicit dependency. Queue 1 also waits for the CPU frame-ready event after the CPU clears the lighting buffer. At frame 3872 the consumer ran at 0.686 ms, the clear at 0.966–0.968 ms, and the producer at 1.282 ms; its release followed at 4.467 ms. Exposure writer `1bba09ec4bc8ff67` has another event dependency. The native SDK's flush/invalidate functions are no-ops for these coherent pools.
- The pale outline around Link is produced before fog, bloom and upscaling, by task `efaa4fa6a80ba719`, mesh `066f5daf12e43c71`, fragment `5ad65c0eefd09c7f`. An offline replay matches both 768x432 RGBA16F targets byte for byte. Removing shared-buffer bytes 48–111 makes direct SH lighting agree with the cached ambient lookup (affected-pixel mean RGB error 0.100/0.136/0.218 falls to 0.0034/0.0020/0.0008): the cache lacked the SH contribution available to the later direct draw. Honoring the event dependency removes the outline, confirmed by the player and later captures.
- A repeating patchy pale layer remained after event ordering was fixed, including with optional attachment discard disabled. [Conditional rendering state lost across queue continuations](../../../docs/reference/rendering.md#conditional-rendering-survives-queue-continuations) caused repeated clears: disabled draws and pending timestamp counter values must survive physical Metal submission boundaries. Fixing both removes the layer in 2,000 asynchronous frames covering a stationary view, loading, camera rotation and movement to the village floor. The loading peak is the normal black-to-scene fade; the camera peak is a foreground branch crossing the view. These bounded samples do not establish every later area is unaffected. Synchronous screenshots wait for the GPU and can hide the original race, so validation uses asynchronous present copies. The rebased delivery subset passes the focused queue, descriptor, continuation, completion, residency and mesh-first-use checks. The current-main shader rebuild and five-game regression are still running at the visual-fix push.

Visual conclusions from those instrumented runs are inconclusive. The event trace, offline producer comparison and combined validation above use the original uninstrumented fragment libraries. The scene flash predates those probes.
